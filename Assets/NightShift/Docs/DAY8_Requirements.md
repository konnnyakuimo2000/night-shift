### 勤務時間（DAY8〜）
- 本番業務は **00:00〜06:00 の6時間**（研修期間は 00:00〜04:00）。
- 実時間の目安: 1ゲーム分＝1.5秒 → 1夜 **約9分**（研修の DAY7 は約8分）。`DayDefinition.realSecondsPerGameMinute` で調整。
- 業務終了の予告は **05:50**（終了10分前）、06:00 で新規受付を停止 → 未処理の要求は短い猶予の後に期限切れ。
- 夜の流れ（緊張の山）:
  | 時間帯 | 様子 |
  |---|---|
  | 00:00〜01:30 | 立ち上がり。普段の要求・問い合わせが中心 |
  | 01:30〜04:00 | 山場。攻撃シナリオ・同時発生が起きやすい |
  | 04:00〜05:00 | 早朝の作業（バッチ処理・海外拠点からの接続などの正常な要求が増える） |
  | 05:00〜06:00 | 朝の出社前。始業準備の要求（VPN接続の増加）と、最後の攻撃の機会 |
- **残業**: 缶コーヒー（消耗品）を持っていれば、06:00 以降も30分だけ勤務を続けられる（新しいイベントは来ない・残りの要求は期限切れにならない・**残業代は出ない＝サービス残業**。罰金を避けるための残業）。
- 給与: 研修の日当 ¥3,000 → 本番は **¥5,000**（6時間・深夜手当込み）。詳細は下の「給与体系」。
- 実装メモ: 画面の「04:00」表記（業務終了の通知・評価画面・DAY表示・業務終了ボタンのメッセージ等）は、すべて `DayDefinition.endMinute` から表示するように直す。

## 1. ランダムイベント

### 1.1 方針
- 1日のイベントは、**日ごとの難易度設定**と**イベントの抽選表**から自動生成する。
- 生成されるすべての要求は、既存の `PolicyEvaluator`（その日のルール＋社員データ）で正解が一意に決まる。→ 解けない問題は出ない。
- 「正常（許可）」と「違反（拒否）」の比率を保証する（全拒否・全許可戦略が通用しない）。
- プレイヤーの行動を学習・適応する仕組みは入れない（DAY1〜5 相当の「人間の攻撃者」設定を維持。AI 攻撃者は後の段階）。

### 1.2 生成の仕組み（案）
```
DailyEventPlanner（その日の計画を作る）
├ 難易度カーブ: 夜の前半は静か → 中盤に山 → 終盤は落ち着く
├ 要求の量:     DayDefinition.requestsPerHour（例: DAY8=6件/h → 徐々に増加）
├ 違反の割合:   DayDefinition.violationRatio（例: 30〜40%）
├ 違反の種類:   ViolationTable（重み付き抽選）
│   ・社員でない利用者 / 他人の端末 / 未登録端末
│   ・権限なし / 管理者権限なし（ローカル管理者のみ 等）
│   ・社外から VPN 以外 / VPN 不許可 / VPN 端末でない
├ 問い合わせ:   相談（二択）・障害（リモート）を抽選。障害は原因のバリエーションも抽選
└ 攻撃シナリオ: ThreatScenario を抽選（1日 0〜2本）。ログで気付ける構成
```
- 同じシードで同じ夜が再現できる（デバッグ・リプレイ用）。
- 同じ社員が短時間に連続しない、前日と同じ問い合わせが続かない、等の重複制御。

### 1.3 データ（拡張）
| データ | 追加項目 |
|---|---|
| `DayDefinition` | `randomEvents`（ランダム生成を使う）, `requestsPerHour`, `violationRatio`, `helpDeskPerNight`, `threatsPerNight`, `intensityCurve` |
| `ViolationDefinition`（新規） | 違反の種類, 重み, 最小日, 生成方法（どの属性を「誤り」にするか） |
| `HelpDeskDefinition` | 既存の `faultVariants` を増やす（Wi-Fi OFF / アダプター無効 / プリンターオフライン / キュー停止 …） |
| `ThreatScenarioDefinition` | 抽選の重み・最小日 |

### 1.4 評価・給与
- 期限切れ・応答時間が評価に効く（研修期間より厳しく）。
- 同時に複数を抱えた時の優先順位判断（セキュリティ警告を後回しにすると減点、など）。

### 2.2 利用できるタイミング（案）

### 2.3 商品カテゴリ

## 3. サブモニター

### 3.1 目的
本番業務では要求・問い合わせ・ログ・リモートが重なる。ウィンドウの切り替えに追われる状況を、**画面を増やして**楽にする（＝お金を払う理由）。

### 3.2 方式（決定）: 見るモニターを切り替える
- モニターごとに**独立したデスクトップ**を持ち、**キーやマウス操作で、いま見るモニターを切り替える**（実際の机にモニターが横に並んでいるイメージ）。
- 並び: `[メイン] [サブ1] [サブ2]` の横並び。サブモニター1台目の購入でサブ1、2台目でサブ2が増える。
- 切り替えの演出: 横にスライド（0.2秒程度）。視点が左右に動く感覚。

### 3.3 操作
| 操作 | 内容 |
|---|---|
| キー | 左右のモニターへ切り替え（既定案: `Ctrl+←` / `Ctrl+→`、モニター番号へ直接: `Ctrl+1〜3`）。キー設定で変更可能 |
| マウス | 画面の左右端にマウスを一定時間置くと隣のモニターへ／タスクバーのモニター表示（□■□）をクリック |
| ウィンドウの移動 | ウィンドウを画面の端までドラッグすると隣のモニターへ移る。タイトルバーの右クリックメニューに「モニター2へ移動」 |

### 3.4 見えていないモニターの扱い
- 時間・イベントは全モニターで常に進む（見えていない側も止まらない）。
- タスクバーにモニター表示（例: `□■□`）を置き、**見えていないモニターに新しい通知・動きがあると点滅**させる。
- 通知（右下のトースト）は、どのモニターを見ていても表示。クリックすると該当ウィンドウのあるモニターへ切り替える。
- タスクバーは全モニター共通（どのモニターのウィンドウもボタンが並ぶ。押すとそのモニターへ切り替えて前面化）。

### 3.5 リモートサポートとの関係
- リモート画面もウィンドウの1つとして、好きなモニターに置ける（例: サブ1にリモート、メインに接続監視）。
- リモート画面を見ている間のキー入力は、これまでどおりリモートPCへ送る。モニター切り替えキーだけはゲーム側で受け付ける。

### 3.6 サブモニターの画面（担当者用ワークステーション）
- **メインモニター** = 会社の「社内情報システム」（今の青いデスクトップ・業務ウィンドウ）。
- **サブモニター** = 担当者用ワークステーションの画面。**社員PC（リモートサポートの画面）と同じ Windows 風の UI**:
  - 青緑の壁紙、デスクトップのアイコン（インストール済みのツール）、[スタート] メニュー、タスクバー、通知領域（時計）
  - ウィンドウの見た目・操作（ドラッグ・最小化・Alt+Tab 相当の切替）もリモートPCと同じ
- サブモニターが2台ある場合は、同じワークステーションの**拡張デスクトップ**（スタートとタスクバーはサブ1にだけ表示）。
- 実装: 既存の `RemoteDesktop`（リモートPC画面）を、担当者用ワークステーションにも使える汎用デスクトップに切り出して再利用する。

### 3.7 ツールアプリはサブモニターに表示
- ストアで買った**ツールはすべて、サブモニターのワークステーションにインストールされる「アプリ」**。
- アプリはサブモニターのデスクトップ・スタートメニューから起動する。**起動している間だけ効果がある**（例: 社員照合アシストを起動しておくと、要求を選んだ時に社員検索へ自動入力）。
- メインモニターの操作と連動する（例: 接続監視で要求を選ぶ → サブモニターの「社員情報サイドパネル」がその社員に切り替わる）。
- **サブモニターが無いとツールは使えない** → 最初の買い物はサブモニター1台目（¥19,800）。ストアでは、ツールに「サブモニターが必要」と表示する。

### 3.8 データ・実装メモ
- `WindowManager` を「モニター単位の作業領域」の集合に拡張（各ウィンドウは所属モニターを持つ）。
- 所持品にサブモニターがあると、`Features` に `MONITOR_2` / `MONITOR_3` が付与される → モニター数が決まる。
- ツールの所持は「インストール済みアプリ」、効果の有無は「そのアプリが起動中か」で判定（`Unlocked(f)` に「起動中のアプリが付与する機能」を加える）。
- 画面はモニター1枚ぶんの大きさを保つ（メイン画面が狭くならない）。

## 4. 業務効率化ツール

### 4.1 原則
- ツールは**情報を集める手間を減らす**だけ。**判断（許可/拒否）を代行しない**。危険な項目を自動で赤くしない。
- **例外①: 自動審査ツール** — プレイヤーが設定した条件をすべて満たす簡単な要求（社内・非管理系・警告なし）だけを自動で許可する。拒否は自動ではしない。自動許可の責任はプレイヤー。攻撃者はその条件の穴を狙ってくる。
- **例外②: サイバー防御AI**（DAY25〜）— 持っているツールを使って許可/拒否を提案・代行する。トークン制限と高コストが歯止め。
- **例外③: ウイルス対策ソフト**（DAY10〜）— 定義ファイルに載っている既知のウイルスだけを検出・駆除する。
- 研修期間で覚えた手順を短縮するもの（例: 毎回の検索を1クリックに）。

### 4.2 ツール一覧
→ **[TOOL_CATALOG.md](TOOL_CATALOG.md)** を参照（10分類・各1〜3個、合計17品目: 機材2・ツール11・AI1・消耗品3〔缶コーヒー・追加トークン・定義ファイル更新〕。接続審査の「自動審査ツール」だけは簡単な要求を自動で許可できる）。
- **最終盤（DAY25〜）: サイバー防御AI** — 購入済みツールをプラグインとして接続して調査・提案・代行する。1夜30,000トークンの制限があり、追加トークンは高価。AI も間違え、攻撃者に騙されることがある（T15）。
