# Claude向け：業務ツールの不具合修正・統合指示

作成日：2026-10-08
対象：Unity NIGHT//SHIFT

## 依頼

以下の不具合を修正し、重複する業務ツールを統合してください。調査だけで終わらず、実装・回帰テスト・ドキュメント更新まで行ってください。
この資料の指摘はコードの静的解析に基づきます。変更前に現在の実装と再現条件を確認し、既に直っている項目は重複修正しないでください。行番号は変わるため、以下のクラス・メソッド名を手掛かりにしてください。

## 制約

- 作業開始時に差分と既存のAGENTS.mdを確認する。他の作業者の変更を戻さない。音響実装も保持する。
- 通常のPolicyEvaluator・審査評価・サブクエストの成立条件を変更しない。自動処理を手動の加担・報酬として数えない。
- 実ネットワーク、外部送信、実ファイルのウイルス検査などは実装しない。対象はゲーム内データのみ。
- コメントは日本語で、既存の構造・記述密度に合わせる。
- 古いセーブの購入権利・無効化設定・残高を壊さない。統合のために同じ機能を買い直させない。
- TOOL_CATALOG.mdは「検討中」の資料であり、すべてが実装済み仕様ではない。現行の商品説明、実装、本資料を照合する。

## 1. 最優先：行選択と操作対象の一致

参照：`Scripts/Runtime/UI/Shift/ShiftDesktop.cs`、`Tools.cs`、`LogViewerView.cs`、`UI/TableView.cs`、`UI/ToolStyle.cs`（パスはAssets/NightShift以下）。

### 1.1 古い要求が新しいログ選択に勝つ

- SelectRequestとSelectLogが別々の選択を保持し、共通のSelectionChangedだけを通知している。
- FirewallConsoleTool.PrefillはSelectedRequestを優先する。要求Aを選んだ後でログBを選んでも、AのIP範囲が入る。
- IsolatorTool.FollowSelectionは要求の端末とログのIPをOR条件で社員一覧に照合する。どちらが優先されるかが社員一覧の順番で決まる。
- 該当端末がない行を選んでも、以前の端末選択が残る。

修正：最後に明示的に選択した対象の種類・データを扱う仕組みを導入する。各画面内の選択を維持してもよいが、連動ツールが参照する対象を曖昧にしない。対象なし・非対応の行では連動先の対象を解除し、実行を無効化する。

### 1.2 無関係な選択で入力を上書きする

メールの選択でも共通イベントが発火し、遮断範囲の手入力が古い要求・ログから上書きされる。選択変更通知を種別で区別する等により、無関係な操作で書き換えない。実行対象IP・端末名をボタン付近に明示し、確認画面と実行処理で同じ対象を使う。

### 1.3 一覧更新時の選択解除

ToolList.SetItemsは選択対象が消えるとSelectedをnullにするが、SelectionChangedを通知しない。連動する詳細・実行ボタンも解除されるよう修正する。ToolList.Selectが一覧にない対象を保持する点も確認する。
TableViewは参照に基づく選択維持と解除通知を既に持つ。正常な維持動作を壊さない。

## 2. VACCINE 99

参照：`UI/Shift/ToolsSecurity.cs` のVaccineTool、SecurityOps、HelpDeskManager、感染イベント。

### 2.1 検査対象の固定

StartScanはREMOTEという種類しか保持せず、Finishがその時点のActiveSession.PCを参照する。Aの検査中にBへ接続するとBが駆除され、切断すると未検査でも「見つかりませんでした」になる。
開始時の対象を固定する。リモート切断・対象切替時は検査を中断し、その理由を表示する。別のPCを駆除したり、未完了を正常終了として表示しない。検査完了後の重複駆除・加点を防ぐ。

### 2.2 ワークステーション検査の空処理

WS検査ボタンは存在するがFinishに対応する分岐がない。既存のワークステーション感染状態・回復手段を追い、実際に検査・駆除へ接続する。感染の別管理を新設して二重状態にしない。
既存の感染モデルに検査対象が存在しない場合は、理由を報告して該当ボタンと商品説明を撤去する。待ち時間だけの機能を残さない。

### 2.3 検出範囲と画面

定義ファイルで検出可能な感染だけを検出する。駆除と破損データの復元を混同しない。サーバー検査についても既存の感染種・対象・商品説明の対応を点検し、未対応の範囲まで保証しない。
ClientとServerは同じアプリを使い、Server商品は「サーバー検査の追加ライセンス」として分かる表記にする。

## 3. SOC-AI

参照：`UI/Shift/ToolsSecurity.cs` のSocAiTool。

### 3.1 無効依頼への課金と対象変更

AskがSpendを先に実行し、1.2秒後のProposeSelectedで初めてSelectedRequestを読む。このため未選択・処理済みにも課金し、待機中の選択変更で対象がすり替わる。
依頼受付時に対象・必要機能・状態・予算を検証し、対象を固定する。完了時に対象が処理済み等になった場合は、実行せず課金を取り消すか、課金前に確定する設計にする。二重返金・二重実行を防ぐ。

### 3.2 プラグイン条件

審査と感染調査のAskはrequiresがnullで、全自動審査にも必要ツールの確認がない。FindInfectionsは内部感染一覧を直接参照している。
審査には自動審査機能、ログ調査にはログ解析機能を必要とする。感染調査は診断・検査機能を通じて得られる情報を使う。ウイルス名の断定にはVACCINEの定義制限を適用し、症状からの疑いと検出結果を区別する。ツール無効化状態も確認する。
所有・有効化していない機能で、内部の正解情報を無料同然に取得させない。既存のAI誤判断・トークン制限は保持する。提案理由に未観測の事実を出さない。

## 4. 購入制限

参照：`UI/Shift/StoreView.cs`、`Core/CareerRecord.cs`、`Data/DefaultDataFactory.MainDays.cs`。

定義更新と追加トークンは購入時にAddItemを通らないが、StockBlockedReasonはItemCountで上限を判定する。

- 追加トークンは1夜最大3回の購入を実際に制限する。使用トークン量と購入回数は別管理にする。
- 定義ファイルが当日版なら追加購入を無効化し、理由を表示する。
- 購入確認後にも上限・残高・前提条件を再検証する。
- 夜の切替とセーブ再読込で制限が正しく維持・更新されるようにする。
- 他の消耗品、とくにお札・コーヒーの制限を変えない。

## 5. ツール統合

以下を基本方針として実装する。統合はアプリの導線と購入権利の整理であり、審査の答えを自動表示する変更ではない。

| 対象 | 実装方針 |
|---|---|
| ログ解析＋相関タイムライン | 同じログ解析アプリのタブにする。基本機能とDAY22以降の相関機能を分ける。相関はIP範囲だけでなく同じ利用者を別IP範囲にまたがって追えるようにする。 |
| リモート診断＋端末隔離 | 端末管理アプリに統合。端末一覧・接続中PCの診断・隔離の導線をまとめる。診断と隔離の権利は分離し、隔離だけ所有する古いセーブも使えるようにする。 |
| メール差出人チェッカー | メール画面のヘッダー詳細に統合し、独立アプリ・新規販売を廃止する。表示拡大や折返しを用意する。送信元表示をIsPhishの正解フラグだけから作らず、メールデータとして管理する。 |
| 遮断コンソール | ログ／接続元の遮断画面に範囲指定を統合する。業務上の解禁日を維持する。独立アプリ・新規販売を廃止する。通常の評価・誤遮断ペナルティを変えない。 |
| VACCINE Client／Server | 同じアプリ＋追加ライセンス方式を明示する。 |
| 社員情報パネル | 独立して維持。選択連動の不具合だけ修正する。 |
| 自動審査、SOC-AI | 今回は別アプリを維持し、上記不具合を修正する。前回の「同一アプリの別モード」は追加案であり必須ではない。性質の違う自動処理を安易に一本化しない。 |
| サーバー監視 | 維持。固定値のメーターを実測の負荷・通信量に見せない。実データがなければ定性的な状態表示に置き換える。 |
| NIGHT CLUB、MIDNIGHT FX、SIGNAL DESK | 今回は統合・削除しない。前2つは別の遊び、SIGNAL DESKは詳細評価が未実施。 |

### 価格と既存セーブ

- 統合するアプリの価格を単純合算しない。基本機能は既存価格、追加機能は既存の権利・解禁日を利用することを初期方針とする。相関機能の価格適正は別途報告し、根拠なく大幅値下げしない。
- メール詳細・範囲遮断の無料統合後も、旧有料商品の所有記録は保持する。購入済みユーザーへの補償額はこれまで未決定のため、自動返金を独自に追加しない。必要なら影響と補償案を完了報告に記載する。
- 旧アイテムIDは移行・読込互換のために必要なら残す。ストア非表示化とID削除は区別する。
- 店舗・スタートメニュー・デスクトップ・説明書・通知・AIのプラグイン一覧を一貫した名称に更新する。
- データ生成を変えた場合はDataVersion、生成済みデータ、商品数テストを整合させる。無関係な生成データ差分を混ぜない。

## 6. 受け入れテスト

既存のEditMode／PlayModeテストの書き方に合わせて追加する。UIテストは可能な限り隔離プロジェクトで実行し、プレイヤーの実セーブを変更しない。

1. 要求A→ログBの選択で、遮断・隔離がBを参照する。社員一覧の順番を変えても結果が同じ。
2. 対象不明のログを選ぶと、前の隔離対象が残らず実行不可になる。
3. メール選択で遮断欄の手入力が変わらない。
4. 一覧更新・絞込・対象削除後に選択表示と実行対象が一致する。残っている対象の選択は維持する。
5. Aの検査中にBへ接続／切断しても、Bを駆除せず、中断と表示する。
6. 検査は既知感染だけを検出し、未検査・中断を未検出と表示しない。駆除の加点が一度だけ。
7. AI依頼の未選択・処理済み・必要ツール不足でトークンを消費しない。
8. AI待機中に選択を変えても対象は変わらない。対象処理済み／終了で消費・返金が重複しない。
9. 必要機能が未所有・無効なら、手動依頼と全自動の双方が使用不可。未知感染を確定検出しない。
10. 追加トークンは3回まで、当日の定義更新は重複購入不可。夜切替・再読込・購入確認後の再検証も確認する。
11. 同じ利用者の別IP範囲のログが相関表示に出る。利用者「-」など不明値を一人として結合しない。
12. 統合前の片方だけを所有したセーブで、購入済み機能が使え、未購入機能は勝手に解禁されない。
13. 廃止商品の所有記録を保持し、移行・再読込で残高が意図せず増減しない。
14. SQ01／SQ02／SQ06の対象要求が自動処理によって手動加担・報酬扱いにならない。
15. 統合画面で対象名・選択行・実行ボタンが見切れず、未解禁時に理由が分かる。

`dotnet build`を通し、関連する既存テストと追加テストを実行する。Unityを実行できない場合は未実施と明記する。成功件数・失敗件数・ログの場所を報告し、ビルド成功だけで動作確認済みとしない。

## 7. 追加実装案：画面への影響が強いウイルスと図鑑

この節はユーザーが追加を希望した実装案。第1〜6節の修正に続けて扱う。下記6種類を設計対象とし、先行実装はBLACK INK・MIRROR・WHITEOUTの3種類を推奨する。残り3種類は後続候補として明記し、全6種類が実装済みであるように報告しない。
V9〜V14は仮ID。既存のVIRUS_CATALOG.md、感染イベント、SecurityOps、HorrorFx、VACCINEの検出定義を読み、既存種との重複とID衝突を確認してから確定する。
感染経路・解禁日・拡大時間はまだ未確定。既存の夜ごとの負荷と対処手段の解禁に合わせて設計し、採用値と理由を仕様書に記録する。実装の都合だけで既存クエストの進行条件を変えない。

### 7.1 ウイルス候補

名称の表記ルール（ユーザー指定）：既存・追加のウイルス／マルウェアの名称は英語のみとし、日本語訳・カタカナ読みを併記しない。ゲーム画面・図鑑・メール・商品説明・仕様書で統一する。症状・対処法などの説明文は日本語のままとする。既存の内部IDやセーブ識別子は、名称表示の統一だけを理由に変更しない。

| 仮ID・名称 | 画面演出 | 業務被害と対処 |
|---|---|---|
| V9 GLASS | ウィンドウに亀裂が入り、内部がタイル状にずれる。拡大すると別画面の断片が混ざる。 | 一部の情報が読みにくくなる。感染端末の隔離・駆除後、ゲーム内の画面再起動で復旧する。 |
| V10 ECHO | 過去の画面が残像として重なり、閉じたウィンドウが戻る。 | 過去の要求の残像と現在の要求の照合が必要。残像はクリックを受けず、日時で区別できる。偽の要求を実際の審査キューへ登録しない。 |
| V11 BLACK INK | 黒いインク状の染みが隅から広がり、文字や顔写真を覆う。 | 放置で読める範囲が減る。隔離で拡大停止、駆除で染みが引く。文書破損を伴う場合は既存のバックアップ復元へ接続する。 |
| V12 MIRROR | デスクトップの中に同じデスクトップが現れ、奥へ複製される。 | 偽警告窓が作業を妨害。本物のタスク管理から複製プロセスを終了し、駆除する。複製画面は演出で、実ウィンドウや処理を無限生成しない。 |

### 7.2 演出とゲーム進行の共通条件

- すべてゲーム内の仮想画面に限定する。OS・実ファイル・実ネットワークには作用させない。
- 演出だけでなく、症状の進行、業務への影響、拡大停止、駆除、残存被害の復旧を区別する。駆除成功だけで破損ファイルまで戻さない。
- 許可／拒否ボタンの位置・当たり判定・対象は変えない。残像・画面断片でクリックを奪わない。偽警告に操作を設ける場合も、本物の審査ボタンと重なる透明な当たり判定を置かない。
- 感染で業務領域が見づらくなる一方、設定・一時停止・復旧操作への導線は残す。判読不能な情報だけを根拠に不可避の誤審査を強制しない。
- 既存の演出軽減設定に対応し、点滅・大きな揺れ・急激な明暗変化を抑える。軽減しても感染の状態・被害・対処条件は同じ。軽減時は静的表示等で症状が分かるようにする。
- 同時感染時の優先順位と重なりの上限を定義する。画面複製・残像・描画素材の数に上限を設け、長時間で増え続けない。
- 隔離・駆除・夜終了・タイトル復帰で不要な演出と入力制限を解除する。描画用オブジェクトの残留で次の夜を汚染しない。
- 定義ファイルの更新前後で検出可否を区別する。SOC-AIや図鑑から未観測の感染を確定表示しない。

### 7.3 ウイルス図鑑「感染記録」

VACCINE 99に「感染記録」タブを追加する。独立した有料ツールは増やさない。VACCINE未購入でもマニュアルから同じ記録を閲覧できる。閲覧権と検査・駆除の実行権は分離する。
既存種と追加種を共通のカタログデータで扱い、名称・検出定義・対処説明を画面ごとに重複定義しない。

| 発見段階 | 図鑑に公開する内容 |
|---|---|
| 未遭遇 | 番号と「未確認」の表示のみ。名称・症状画像・対処のネタバレを出さない。 |
| 症状を観測 | 症状画像、短い観測記録、初遭遇日。原因は未確定として扱う。 |
| 検出に成功 | 名称、感染経路、対応する定義ファイルを公開する。 |
| 駆除に成功 | 有効だった対処と、駆除後に残る被害を記録する。 |
| 復旧完了 | 「対応済み」の印と、その夜の対応履歴を残す。 |

ページの共通項目は「症状画像／危険度／感染経路／拡大条件／対処／復旧方法」。各段階で未解放の項目は未確認表示にする。危険度はカタログ上の説明であり、現在の感染を自動判定する警告にはしない。
表示異常とデータ破損を明確に区別する。画像はゲーム内の症状を示す静止画・専用プレビュー等とし、図鑑閲覧で実際の感染・加点・演出被害を発生させない。

発見記録はキャリアに保存し、再読込しても維持する。新規ゲームでは既存のキャリアリセット方針に従う。旧セーブでは未記録項目を安全に初期化する。
既存の検出不能種や、ウイルスではない事象にVACCINEでの検出・駆除を強制しない。その種に合う調査・封じ込めの達成イベントを使い、「駆除」と誤記しない。
再感染で過去の解放項目は失わない。「過去に対応済み」と「今回の感染が解決済み」を区別する。観測・検出・駆除・復旧の通知が繰り返されても履歴や報酬を重複させない。

### 7.4 雨宮リカの記録

図鑑の末尾に「分類不能の観測記録」として扱う。通常ウイルスと断定せず、VACCINE更新・駆除で解決できるとは表示しない。
遭遇に伴って文章や画像が変化する演出を追加できる。ただし、謎解きの必須情報を消す・書き換えて解けなくする・未到達の展開を先に表示することは禁止する。

### 11.2 最優先：駆除しても活動・拡大・暗号化が止まらない

VaccineToolは感染情報を削除するが、ThreatScriptsのBEACON／SPREAD_CHECK／RANSOM_WRITE／RANSOM_CHECKは主にDisconnectedだけを確認する。このため、接続状態のまま駆除に成功しても後続の被害が発生し得る。

- 感染端末・種類・必要なら感染の発生単位を照合し、その感染が現在も有効な場合だけ後続処理を実行する。
- 感染の終了をシナリオへ伝えるか、各処理で有効性を確認する。どちらでも、駆除済みの古い予約処理が再感染後の別の感染を進行させないようにする。
- 駆除で将来の被害を止める一方、発生済みの暗号化・破損・漏えいは消さない。隔離による活動停止と駆除を区別する。

### 11.3 高：隔離端末へ拡大し、感染ゼロでも被害を記録する

SPREAD_CHECKの拡大先は在籍・勤務・感染済みを確認するが、隔離や通信切断を確認しない。また、拡大数がゼロでも被害を記録する。

- 感染元と感染先の双方について、経路上の到達可能性を確認する。隔離・切断した端末を拡大先にしない。
- 実際に新規感染した件数に応じて被害・ログ・図鑑の観測記録を更新する。対象ゼロなら「感染が広がった」と記録しない。
- 別のウイルスによる既存感染を上書きして消さない。同時感染を非対応とする場合も、既存状態を保持する一貫した規則を明記する。

### 11.4 高：持ち越しで種類が混ざり、隔離が駆除になる

ScheduleCarriedInfectionsは元のIDを復元する一方、全種類に共通のSPREAD_CHECKを設定し、周囲へV3を感染させる。NightClosingでは隔離端末とNIGHT-OPS-WSを保存対象から外している。

- 感染種とその進行状態を保存し、翌夜も種類に合う処理を再開する。TINNITUSやBRIAR ROSEを理由なくNIGHTCRYの拡大処理へ変換しない。
- 感染状態と隔離状態を分けて保存する。隔離しただけで翌朝に感染を消さず、活動停止中の感染として保持する。駆除済みは持ち越さない。
- 担当者ワークステーションとサーバーも対象識別・保存・回復経路を確認する。社員検索に見つからないから黙って感染を捨てる実装にしない。
- 旧形式の `ウイルスID:端末名` を互換読込する。過去に保存されなかった感染は推測で復元しない。
- 夜開始処理や読込の繰り返しで感染・予約イベントを重複させない。日・週のやり直しでは対応する開始時点へ戻す。

### 11.5 高：侵入前の遮断がサーバー侵入を止めない

GARBLEのWEB_IMPLANTは予定時刻にプロセスを配置する。ThreatScenarioManagerの遮断判定は主にTraffic／LogEntryに作用し、Scriptの侵入処理は通過する。

- 探索後、侵入前に攻撃元を遮断した場合は、その接続を使う侵入を成立させない。関連IPを使う場合は実際の接続元を照合する。
- 侵入が成立した後は、外部IPを遮断しただけで配置済みのマルウェアを駆除しない。活動停止・駆除・復元の役割を分ける。
- Scriptを一律に遮断で停止する変更は避ける。内部で既に稼働している処理や防御側の復旧処理まで止めない。段階と必要な通信経路ごとに判定する。

### 11.6 中：添付の実行済みと報告済みが混同される

PhishingMail.OpenAttachmentは二重実行防止としてReported=trueを設定し、誤って開いた後の報告を禁止してしまう。

- 「実行済み」「報告済み」「対策ソフトによる阻止」を別状態として扱う。必要なら既存メールモデルに最小限の項目を加える。
- 添付実行後も報告でき、実行・報告の双方が一度だけ適用されるようにする。報告しても既に発生した感染や被害を取り消さない。
- 定義が対応しているVACCINEで阻止した場合は感染しない。未対応時はゲーム内の感染が成立する。再クリックで重複感染・加点・被害を発生させない。

### 共通の設計条件

「侵入 → 感染 → 活動・拡大 → 隔離 → 駆除 → 復旧」の状態を整理する。ただしこれは説明上の順序であり、必ず隔離しないと駆除できない等の独自条件を加えるものではない。
経路ごとに発生条件・手がかり・対処猶予・防御手段・残存被害・翌夜の状態を仕様書へ記載する。説明上は防げるのに実装では防げない経路を残さない。名称は英語のみとし、実ネットワーク・実ファイルには作用させない。

### 追加の受け入れテスト

43. NIGHTCRYを拡大前に駆除すると、その感染に由来する定期通信・拡大が停止する。BRIAR ROSE駆除後も追加暗号化・致命的被害が起きず、既存の暗号化記録は残る。
44. 拡大先が全て隔離・切断・対象外なら新規感染も拡大被害もゼロ。接続可能な端末がある場合だけ、実際の感染数に対応した記録が残る。
45. 各種類の持ち越しでID・進行・隔離状態を保持し、別種類へ変化しない。駆除済み感染は戻らない。ワークステーション・サーバー・旧形式セーブも確認する。
46. 感染保存の再読込・夜開始の再実行で感染と予約処理が重複しない。駆除後の再感染に古い感染の予約処理が作用しない。
47. GARBLEの侵入前に実際の攻撃元を遮断するとプロセス配置を阻止する。配置後に遮断しても駆除済みにはならず、正しい駆除・復元手段で回復できる。
48. 添付実行後にも一度だけ報告できる。連打で感染・被害・報告の評価が重複しない。対応する定義では阻止し、未対応なら感染する。
49. 経路A・Dの仕様対象について、許可／拒否、仮想ファイル実行／未実行と感染結果が一致する。Dは実ファイルを実行しない。
50. 経路Eのアカウント侵害と通常感染の回復を混同しない。経路Hは手がかりと阻止条件を検証し、残る未確認事項を明記する。

### 残した制約とその理由
- バックアップ喪失の信用の減点は、処理順を変えても以前と同じ合計（−3）になるよう、汎用の被害の減点と「被害ゼロの夜 +2」からは除いて数える。夜の記録（damaged）と評価の被害件数には含める（評価のランクが下がる場合がある）。
- 旧形式の週のスナップショットにはアカウントがないため、週のやり直しでは今のアカウントのまま（過去のパスワードは推測しない）。
- サーバーの GARBLE は夜をまたいで持ち越さない。メールサーバー → TINNITUS（経路 A）は感染させる端末がないので未接続。
- リモート管理の接続は隔離しても残る（ゲームの操作モデルを維持）。画面・通信可否・完了判定は `Quarantined` で一致させた。
- 新しい問い合わせ（T16〜T18）には試験の出典を付けていない（対応する過去問題を確認していないため）。
- 経路 H は T14 の止まり方（範囲の遮断・試行上限）と手がかりのログを確認した。最終夜の結果判定とのつながりはテストしていない。
